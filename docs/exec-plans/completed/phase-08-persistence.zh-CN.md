# Phase 08——SQLite 持久化

状态：已完成。依据：`ARCHITECTURE.md`、`docs/data/DATA_CONTRACT.md`（`0.1-draft`）和 `AGENTS.md`。

## 范围

为四个规范化数据集及来源/规范化证据实现一个具体的 SQLite 仓储。仅接收完整且成功的 `ValidationResult`。以原子事务替换当前演示数据；规范化业务内容等价时不写入。返回一致的读取快照，并提供日期、生产线、产品和订单筛选，不向分析层暴露 SQL。不实现仪表盘或 KPI 计算。

## 方法

1. 定义简洁、带版本的 SQLite 模式，包含批次身份、来源元数据、规范化证据及四个数据表。三位小数以精确文本保存，设置业务键唯一性和外键。
2. 按数据合同第 8 节序列化规范业务内容并计算哈希，使等价性不受文件顺序或格式影响。
3. 在同一个显式事务中写入所有记录并切换活动批次。失败时回滚，不发布部分批次。拒绝未验证尝试、模式版本不匹配及不兼容的合同版本。
4. 在同一个读事务中返回完整或筛选后的领域记录。生产按包含端点的业务日期及可选生产线/产品/订单筛选；库存仅按包含端点的快照日期筛选。
5. 使用临时磁盘 SQLite 进行集成测试：空库、插入/重开/读取、筛选、替换/无操作、来源和关系、拒绝批次/回滚/模式不匹配。
6. 运行 `ruff check .` 与 `pytest -q`，记录证据，通过后移至 `completed/`。

## 决策与限制

- 用户明确要求实现持久化层。数据合同 C06 仍是草案产品决策；本实现遵循其已记录的整批替换行为，但不声称获得全局批准。
- 查询方法只检索记录。订单生命周期指标、库存到产品的关联和 SQL KPI 聚合均不在本阶段范围内。
- 必须显式初始化仓储才能创建数据库；未知的现有模式不会被自动重置。

## 验证证据

- `ruff check .`：全部通过。
- `pytest -q`：40 项通过，包含磁盘 SQLite 集成测试。
- 已初始化空库不含活动批次。已验证数据插入后关闭并重开连接，四域来源信息和精确 `Decimal` 值均可读回。
- 包含端点的日期、生产线、产品和订单筛选返回预期的匹配生产槽位；库存日期筛选独立执行。
- 行顺序变化的 CSV 与内容等价的 XLSX 均不重复写入；内容变更时替换活动批次。拒绝输入和受约束写入失败均保留旧批次。
- SQLite 外键检查无违规。模式版本不匹配时拒绝访问且不重置数据。完整 5,220 行合成批次已落盘并读回。
- 分析、服务和 UI 层没有新增 SQL；没有新增仪表盘或 KPI 代码。
